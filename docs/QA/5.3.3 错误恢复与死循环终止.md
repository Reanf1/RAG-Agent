# 5.3.3 错误恢复与死循环终止

## 1 范围与参考

在现有手写 ReAct、快速路由和独立批次上补充三项：工具超时限次重试或跳过，执行异常后的替代规划，重复调用与迭代上限终止。保留本科生项目的简单函数组织，无新增依赖、服务、调度图或 Agent 框架。

修改前读取固定参考版本的 [app/core/agent.py](https://github.com/dsy1018/ai-chatbot/blob/6979d7173ed0f92910a8571dd4ca1b4a171a2c49/app/core/agent.py)、[tests/test_tools.py](https://github.com/dsy1018/ai-chatbot/blob/6979d7173ed0f92910a8571dd4ca1b4a171a2c49/tests/test_tools.py) 及 API 测试。沿用注册表查找、真实 invoke、异常记录和原生工具消息。上游只有一轮执行，没有同步工具等待上限、限次重试、异常替代和循环检测；本次补充属于课程要求。

## 2 实现与边界

代码在 [router.py](../../src/agent/router.py)、[tools.py](../../src/agent/tools.py)、[react_loop.py](../../src/agent/react_loop.py)，配置统一在 [config.yaml](../../config.yaml)：

| 配置 | 默认值 | 行为 |
| --- | --- | --- |
| tool_timeout_seconds | 300 秒 | 单个逻辑工具调用的总等待预算，包含重试；并行调用各自从提交时计时，不因按顺序收取结果而重新获得等待预算 |
| max_tool_retries | 1 | 已结束的真实超时异常最多再执行一次；设为 0 可关闭重试 |
| max_repeated_calls | 2 | 同一请求内，相同工具名和规范化参数最多执行两轮，第三次在执行前拦截 |
| max_iterations | 8 | 整个 ReAct 请求的轮数上限，包含替代规划；最后一轮完成仍算成功 |
| max_parallel_calls | 2 | 仍限制独立批次数和线程数 |

### 超时重试与跳过

`execute_tool`保留单次实际执行行为。它补充error_kind分类：timeout、input、execution。TimeoutError、httpx超时，以及通过显式异常链或URLError.reason包装的超时才分类为timeout；不凭错误字符串中是否出现“timeout”猜测。参数/类型、文件缺失和算术输入错误不自动改换工具；其他执行故障可以重新规划。

`execute_calls`监督有限次执行。已返回的超时异常，在总预算和重试次数允许时串行重试，保留每次attempt、status、error、error_kind和耗时。逻辑调用仍对应原call_id和一条最终ToolMessage，重试成功不抹掉第一次失败。非超时异常直接记录，不盲目重复。当前本地科研工具为查询/分析工具；如以后增加具有写入副作用的工具，应先明确幂等性，再决定是否允许自动重试。

等待预算到期时返回error_kind=deadline、pending=true的错误结果，停止等待和后续重试；其他按时完成的独立结果继续保留。超期的成功也不采用。run_react以tool_timeout结束当前请求，不再调用Observation模型或启动下一轮，防止同一请求不断积累未退出的后台调用。这里的pending表示结果因超期被跳过，不证明函数被取消。

**线程限制**：Python同步线程无法强制取消正在运行的函数。关闭线程池使用shutdown(wait=False, cancel_futures=True)，只取消尚未启动的工作；运行中的函数可能继续执行，其迟到结果不会写回本次Agent Context，但函数本身已有的日志等副作用仍可能发生。Python进程退出也可能等待这些线程，不能宣称已强杀工具或底层服务。底层HTTP继续使用自身超时。上述区别依据 [Python 3.10 concurrent.futures 官方文档](https://docs.python.org/3.10/library/concurrent.futures.html)。

### 异常记录与替代规划

每次最终结果及全部重试错误保存到事件与Context.observations，包含工具名、原参数、call_id、真实错误分类、attempts与实际耗时，原生AIMessage/ToolMessage关联保持完整。这是本阶段的结构化错误轨迹；会话持久化与前端监控仍按后续模块实现。

执行异常或已结束但重试耗尽的超时后，将失败工具名加入本请求的禁用集合，Context.recovery记录failed_tools、available_alternatives和pending。Observation仍读取实际失败消息，不允许标记成功；有其他注册工具且还有迭代预算时，程序发出recovery事件并提供下一轮替代规划机会，保留原模型Observation事件。Thought与Action的工具描述/Schema都移除已禁用工具；由本地模型判断哪些剩余工具能完成**原任务**，再生成真实参数、执行并观察。

不硬编码“元信息→摘要”等并不等价的替代，不自动开启联网，不转云端。没有适用的替代工具时可以直接说明未完成；替代也失败时继续禁用该工具，最终受实际工具数量和迭代上限约束。未执行替代而直接回答时不能宣称故障已恢复。每个替代调用使用新的call_id，原失败和新结果各自保留，不能把备用结果伪装成原工具成功。

### 重复调用终止

按工具名与排序后的JSON参数记录本请求内的执行轮数；相同参数但键顺序不同视为同一调用。计数不受模型控制，也不跨请求共享。相同工具的不同参数正常执行；多次独立用户请求不互相影响。

到达重复阈值后，Action发出错误提示，done.stop_reason=repeated_calls，task_complete=false，提示检测到可能死循环并请用户补充资料或缩小问题。A→A→A和A→B→A→B→A都能提前终止。不断更换参数的无效执行仍由max_iterations兜底。重复阈值是可解释的保守规则，不宣称能识别任意语义循环；确有重复读取需求时可以调整参数或阈值。

## 3 验证结果（2026 年 10 月 2 日）

### 自动化验证

新增23项有意义的测试，工具函数与线程实际执行，模型HTTP明确隔离。覆盖：

- 已结束超时后一次重试成功、持续超时恰好两次、关闭重试、非超时不重复、包装超时与文字误判。
- Event控制的真实阻塞：预算到期时函数仍未退出，结果立即跳过；释放后不出现重复执行/迟到结果回写。
- 并行一项超时仍保留另一项成功；关闭生成器不等待后台函数，不启动迟到重试；Agent不再启动后续模型或工具。
- 异常后的实际备用调用、独立call_id、失败轨迹保留、输入状态不变；重试耗尽可替代；无替代/无适用替代/所有替代失败诚实结束；模型不能重新选择已禁用工具或虚报完成。
- 相同调用及交替循环的提前拦截，不同参数及独立请求允许执行；非法上限在模型/工具执行前拒绝，恢复不越过最后一轮。

最终：检索165项、生成123项、Agent157项，**全部445项通过，耗时17.663秒**。记录见 [完整验收日志](../../reports/错误恢复验收测试_20261002.log)。`pip check`通过。

首轮134项回归发现：新增签名计算提前拒绝NaN，使既有“非法参数作为tool_result返回”的格式改变；随后恢复执行器的原校验边界，保留无副作用和真实工具错误格式。初次失败、20项专项和首次442项全量记录分别保留于[初次日志](../../reports/错误恢复初次测试_20261002.log)、[专项日志](../../reports/错误恢复专项测试_20261002.log)、[首次完整日志](../../reports/错误恢复完整测试_20261002.log)，没有覆盖失败记录。

三项全部通过。见 [真实核验JSON](../../reports/错误恢复真实核验_20261002.json)、[运行日志](../../reports/错误恢复真实核验_20261002.log) 和 [复现脚本](../../reports/verify_error_recovery.py)。阻塞跳过与循环强制终止使用确定性自动化测试核验，未把模型主动避免循环冒充故障检测实验。
