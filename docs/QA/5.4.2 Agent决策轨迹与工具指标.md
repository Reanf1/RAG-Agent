## 2. 全链路轨迹

每个请求的`metrics.trace`按事件到达顺序记录公开说明与实际执行事实，页面按轮次展开：

| 事件 | 页面内容 |
| --- | --- |
| thought | 有限长度的决策说明、下一步、计划工具及路由方式 |
| tool_call | Action工具名、真实调用ID与参数；共享模型Action生成的多个调用分别保留 |
| tool_result | 调用ID、实际结果或错误、执行方式、耗时、各次尝试与后台未结束说明 |
| observation | 对实际结果的公开判断、继续/结束决定和任务是否完成 |
| action_skipped | 直接回答等路径跳过工具执行的原因 |
| recovery/error | 失败说明、失败工具及可选替代工具，保留在所属轮次 |
| done | 最终终止原因与任务完成标志，归入最后一轮 |

轨迹只复制白名单字段；原生AIMessage/ToolMessage、完整Context和模型私有推理字段不进入轨迹。Thought与Observation展示已有的简短决策说明，不要求模型披露私有思维过程。工具结果按实际返回展示，不用预先编写的说明代替。参数、结果与尝试记录可在JSON组件中展开。

并行结果沿用执行器按声明调用顺序输出的规则；它是Agent实际收到并观察的顺序，不能据此推断两个后台线程谁先结束。准备阶段错误归入“请求准备与终止”。记忆摘要用量继续单列，不冒充ReAct工具步骤。

## 3. 工具指标口径

当前请求的`metrics.tool_calls`以`call_id`关联Action与返回，`metrics.tools`汇总当前请求和按工具名的统计；不同轮次的新ID计为独立调用。

```text
工具调用成功率 = 最终status为success的逻辑调用数 / 已返回最终success或error的逻辑调用数
平均工具耗时 = 已返回调用中有实际有效耗时的值之和 / 这些调用的数量
```

- Action发出表示“已计划”，可能尚未实际派发。未返回调用显示“待返回”，不进入成功率分母；没有样本显示“暂无已返回调用”，不显示虚假的0%。
- 执行器给出的最终状态决定成功/失败。RAG低相关性返回`needs_confirmation`仍可能是执行成功，但任务未完成；成功率不能代替任务完成率、回答正确率或引用准确率。
- 限次重试按同一个call_id最终状态计一次；尝试次数与每次成功/失败/耗时保留，第一次失败后重试成功算一个成功调用。重复接收同ID结果不会新增工具计数。
- 耗时来自执行器`elapsed_seconds`，包括工具执行及限次重试；等待超时记录已实际等待的时间和失败。成功与失败都参与均值，缺失/无效耗时保持未知，不能用0填补。
- 超时返回`pending=true`表示Agent已经停止等待、判定本次调用失败，后台函数可能仍运行；它不表示线程已被杀死，也不接收迟到结果。
- 并行调用各自计时、时间可以重叠；平均耗时与耗时之和都不能当作Agent端到端延迟。后者仍由既有`response_seconds`独立测量，包含模型推理与会话准备/保存。

页面显示本次请求的成功率、平均耗时、逐调用明细及按工具汇总；每个阶段刷新，最终快照在页面重跑时重绘，不再调用模型或写日志。历史运行统计不新增为另一套全局累计账目。

## 4. 日志与调用方法

会话入口继续向`logs/agent_YYYY-MM-DD.jsonl`追加阶段快照，`metrics`中现在包含`trace`、`tool_calls`及`tools`。同一请求有多条快照，读取历史时应取相同request_id的最新快照，不能将各阶段计数相加。

```python
from src.agent import MemoryManager, run_session

memory = MemoryManager()
session = memory.create_session("demo")
for event in run_session("调用calculator计算3.14*2.56", "demo", session, memory=memory):
    # 一次事件对应一个独立快照，适合直接刷新页面。
    print(event["metrics"]["tools"])
    print(event["metrics"]["trace"][-1])
```
