# 5.1.3 向量数据库对比与选择

## 结论

本项目选择 **Chroma 0.5.23**，沿用参考仓库的 `langchain-chroma==0.1.4`，使用本地持久化、余弦距离与 `search_ef=100`。业务只保留 Chroma 操作封装；FAISS 仅出现在独立对比实验中。

选择依据是本科项目的实现工作量：Chroma 同时保存向量、正文和来源字段，提供元数据过滤与删除接口。FAISS 在本轮的查询速度、内存索引写入速度和磁盘占用上均更好，但需要配套管理正文、来源和字符串块 ID。Chroma 不是性能胜者；它在本次小型论文库中满足预先声明的质量、延迟条件，且更适合沿用已有代码。

**不能直接使用 Chroma 默认搜索参数。** 默认 `search_ef=10` 的 Top-5 相对精确检索一致率为 91.04%，未达到 99% 门槛；保留首轮结果后，仅将该参数提高到 100 复测，一致率达到 100%，三轮查询 P95 均低于 1.31 毫秒。

## 资料与参考代码

- [Chroma 官方写入说明](https://docs.trychroma.com/docs/collections/add-data)：支持一起保存正文、元数据和显式向量。本轮显式传入预计算 M3E 向量，避免默认模型下载，也不重复计算 Embedding。
- [Chroma 官方删除说明](https://docs.trychroma.com/docs/collections/delete-data)：支持按 ID 或元数据条件删除记录。业务按 `doc_id` 删除，原始文件管理由后续集成负责。
- [Chroma 0.5.23 的 HNSW 参数源码](https://github.com/chroma-core/chroma/blob/0.5.23/chromadb/segment/impl/vector/hnsw_params.py)：该版本默认 `search_ef=10`、`construction_ef=100`、`M=16`、批大小 100、同步阈值 1000。本实验保留后三类默认设置，距离改为 cosine，线程数固定为 4。
- [FAISS 官方距离说明](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)：文档和查询均归一化后，内积检索等价于余弦相似度。本轮采用 `IndexIDMap2(IndexFlatIP(768))`，作为精确检索对照，没有用近似 FAISS 索引。
- [FAISS 官方索引读写说明](https://github.com/facebookresearch/faiss/wiki/Index-IO,-cloning-and-hyper-parameter-tuning) 与 [ID/删除操作说明](https://github.com/facebookresearch/faiss/wiki/Special-operations-on-indexes)：索引通过 `write_index/read_index` 保存和读取；正文、来源与字符串 ID 映射另存 JSON。
- 参考仓库固定提交的 [app/core/rag.py](https://github.com/dsy1018/ai-chatbot/blob/6979d7173ed0f92910a8571dd4ca1b4a171a2c49/app/core/rag.py)：核对 `_init_vectorstore()`、`add_to_vectorstore()`、`_retrieve_vector()` 与读取全部块的流程；同时阅读 `tests/test_rag.py` 和测试夹具。上游使用随机 UUID，本项目改用已有分块模块的稳定 `chunk_id`，防止重复导入重复编码。上游 mock 检索测试不能证明实际数据库持久化，本轮补真实数据库验证。

官方当前文档用于确认操作含义；具体接口、参数与元数据限制同时按本机安装的 0.5.23 源码核验，不使用新版本特有能力。

## 实验方法

日期：2026 年 9 月 29 日。机器：Mac mini、Apple M4、16 GiB 内存；Python 3.10.10。版本为 NumPy 1.26.4、Chroma 0.5.23、langchain-chroma 0.1.4、FAISS CPU 1.9.0.post1、PyTorch 2.5.1。模型仍为 YAML 固定版本的 `moka-ai/m3e-base`，CPU、FP32、4 线程、批大小 32，输出归一化的 768 维向量。

复用 [Embedding 双语评测集](../../reports/5_1_3%20向量化与存储/Embedding论文双语评测集.json) 的 3 篇中文、3 篇英文人工智能论文：默认递归 512/64 字符切分后的 821 个块，48 个意图的中英文配对问题共 96 条，四种语言方向各 24 条。问题与相关段落由 Codex 根据原文编写，尚未经人工复核。所有论文块共同参与检索，不根据问题预筛选来源。

样本 SHA-256：`63c22eddcf08f05b809dd888b4794993ea0364edf7d43d0c442e16ae76342707`。两轮实验复用完全相同的向量文件，文件哈希见结果 JSON。模型加载、文档与查询编码合计约 70.20 秒，**不计入数据库计时**。

选型前声明的条件：Chroma 的 Top-5 相对精确检索一致率至少 99%，且查询 P95 小于 20 毫秒时，优先采用实现简单的 Chroma；不满足时重新权衡。首轮默认参数未通过，随后只调整 `search_ef` 复测，没有降低阈值或改变评测样本。

实验流程如下：

1. 一次生成 M3E 文档、查询向量，保存统一 float32 数组。归一化误差小于 1e-5，全部数值有限。
2. 每种配置使用三个全新目录，交替执行 Chroma/FAISS，先写入 738 块，再增量写入剩余 83 块。
3. 预热一条查询；每个建库轮次完整查询三遍，共计每种配置 864 次逐题 Top-10 查询。计时包含 SDK 与 ID 映射，不包含 Embedding，也没有给 FAISS 使用批量查询加速。
4. 删除首篇论文的 94 块，确认剩余 727 块，然后恢复。FAISS 整数 ID 映射到稳定块 ID；Chroma 按元数据 `doc_id` 删除。
5. 在独立 Python 进程重新打开索引，检查 821 块、完整正文/来源和全部问题的 Top-10 排名。删除恢复可能改变近似索引图，因此重启排名与恢复后的排名比较。
6. 统计删除恢复之后的实际数据库文件大小。Chroma 的核验用 `records.json` 副本排除；FAISS 必需的正文/来源 JSON 计入。

实验来源字段用 `paper_id` 作为 `doc_id`，以 `paper_id.pdf` 作展示文件名，并保留页码、字符区间等。业务封装不替换加载器产生的真实文件 SHA 文档 ID 和文件名。

## 真实结果

除一致率与质量指标外，表中数值为三个建库轮次的中位数；查询 P50/P95 先在每个轮次的 288 次查询上计算，再取中位数。

| 指标 | Chroma 默认 ef=10 | Chroma ef=100（选定） | FAISS FlatIP（复测轮） |
| --- | ---: | ---: | ---: |
| Top-5 相对精确检索一致率 | 91.04% | 100.00% | 100.00%（精确对照） |
| 查询 P50，毫秒 | 0.910 | 1.147 | 0.050 |
| 查询 P95，毫秒 | 2.113 | 1.205 | 0.053 |
| 初始写入 738 块，毫秒 | 412.331 | 411.614 | 0.413 |
| 增量写入 83 块，毫秒 | 56.301 | 55.778 | 0.198 |
| 删除 94 块，毫秒 | 38.337 | 39.084 | 0.072 |
| 数据库及必要正文文件，MiB | 13.256 | 13.256 | 3.316 |
| 新进程打开并读取核验数据，毫秒 | 369.197 | 380.739 | 0.375 |
| 问题标注 Hit@5 | 30.21% | 34.38% | 34.38% |
| 问题标注 Recall@5 | 29.51% | 33.16% | 33.16% |
| 问题标注 MRR@10 | 0.1986 | 0.2264 | 0.2264 |
| 数量、删除与重启核验 | 通过 | 通过 | 通过 |

Top-5 一致率定义为每题 Chroma/FAISS 前五项集合交集数除以 5，再汇总三轮；它衡量近似索引是否遗漏精确检索候选。**100% 一致率不是 100% 问答正确率，也不是人工相关段落 Recall@5。** Hit、Recall 与 MRR 根据原有问题标注另外计算，模型跨语言质量不足仍然存在。

FAISS 的写入和删除行主要计量内存索引操作，Chroma 则包含数据库写入，不能把这些数字解读为等价的全流程落盘速度。FAISS 在复测中保存索引及正文 JSON 另需约 6.72 毫秒；Chroma 自动持久化，无需手工 `persist()`。原始结果中的 `explicit_save_ms` 对 Chroma 只是生成核验副本的耗时，不是独立落盘耗时，不用于选型。新进程检查的加载耗时不包含 Python/库导入和 FAISS 正文 JSON 读取，且操作系统文件缓存未清空，不属于冷启动总延迟。未测峰值内存、百万向量或多用户并发，不能据此宣称 Chroma 大规模性能优于 FAISS。

复测 Chroma 三轮 P95 为 1.302、1.201、1.205 毫秒，均满足 20 毫秒门槛。默认参数首轮原始结果中 `selected=faiss`，复测中 `selected=chroma`；两份结果均保留，最终配置采用通过同一门槛的 `search_ef=100`。

## 操作封装与验证

实现位于 [vector_store.py](../../src/retrieval/vector_store.py)，保持原目录，无额外服务或后端选择框架：

| 接口 | 行为 |
| --- | --- |
| `get_embeddings()` | 按需缓存本地 M3E，不下载权重、不转云端 |
| `VectorStore()` | 按 YAML 打开/创建本地 Chroma 集合；默认目录 `data/index/`。当前模型延迟到有效向量写入/查询才加载，读取正文无需权重 |
| `add_chunks(chunks)` | 稳定 ID 去重，分批写入，仅编码新块，返回实际新增数量 |
| `search(query, k=None, doc_id=None)` | 返回 `[(Document, cosine_score)]`，默认 Top-5，可限定文档；空库/空问题返回空列表 |
| `count()` / `list_chunks(doc_id=None)` | 读取块数、正文和来源，不重新编码；数据库异常不吞掉 |
| `delete_document(doc_id)` | 同步删除该文档的向量、正文和元数据，返回删除块数；保留原始文件 |

同一批次先检查必要文档/块 ID。已有 ID 跳过；两篇文档正文相同时仍保留两个来源。集合记录模型名、revision、余弦距离和索引参数，配置不匹配时明确要求在新目录重建；不静默混用旧向量。余弦分数不是置信概率，本轮不套用上游的固定 0.3 阈值。

新增 12 个接口测试，数据库使用真实临时 Chroma；小型二维 Embedding 只用于验证可预期的排序和是否重复编码，不用于性能结论。覆盖空库、正文/来源回读、负相似度、Top-K 与文档过滤、重复导入、增量写入、删除、重开、模型/参数不一致、无效 ID/参数、相同正文的不同来源、真实 Markdown 加载和超过 500 块的批量写入。全部 **96 个测试通过**。

另在 `HF_HUB_OFFLINE=1` 下用真实 M3E 完成 Markdown 加载→分块→新增→重复导入→中英文查询→重开→删除检查。示例原文与查询相似度分别为 0.812360、0.791011，仅证明接口可运行，不作为模型质量评测。

## 环境问题与复现

适配器要求 `numpy<2`，因此将项目 `.venv` 的 NumPy 从 2.2.6 调整为 1.26.4。Chroma 0.5.23 使用旧的 PostHog 调用接口，固定 PostHog 3.25.0，并关闭 Chroma 遥测。`pip check` 通过，现有测试与真实 M3E 均通过验证；Chroma 安装的 FastAPI 等是传递依赖，本项目不启动 FastAPI 或数据库服务器。

本机复现到 FAISS 1.9.0.post1 与 PyTorch 2.5.1 同进程加载后，M3E 在 `layer_norm` 编码处发生段错误；单独运行 M3E 正常。原因尚未确认，不扩大为所有平台的结论。实验脚本用独立进程准备向量，再由数据库实验读取同一 NPZ；业务不导入 FAISS，真实 Chroma+M3E 已验证正常。当前 Pydantic 2.13.5 对旧 Chroma 的字段读取发出弃用警告，测试通过，本轮未升级相关库。

在项目根目录执行：

```bash
# 业务依赖只包含选定的 Chroma；对比时额外安装 FAISS。
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip install --no-cache-dir faiss-cpu==1.9.0.post1

# 需要已准备的论文样本和 M3E 权重；样本准备方法见 Embedding QA。
# 第一条重新编码并复现默认参数，第二条复用已校验的同一批向量。
.venv/bin/python "reports/5_1_3 向量化与存储/compare_vector_stores.py" --search-ef 10 --output "reports/5_1_3 向量化与存储/向量数据库默认参数对比结果.json"
.venv/bin/python "reports/5_1_3 向量化与存储/compare_vector_stores.py" --search-ef 100 --reuse-vectors

.venv/bin/python -m unittest discover -s tests -p 'test_retrieval.py' -v
.venv/bin/python -m pip check
```
